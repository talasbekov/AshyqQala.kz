# AshyqQala.KZ — Спецификация use cases (v4, full, development-ready)

Единый документ для команды, жюри и **передачи разработчикам**. Объединяет v3 (UC-01…UC-35) и v3.1 (UC-36…UC-38, уточнённые статусы, модель данных, правила) в один источник, добавляет UC-39 (назначение куратора), SLA реакции куратора и единое правило обязательной причины. Патчи раздела E из v3.1 применены прямо в тексте UC — отдельно их применять не нужно.

> **Правила формулировок (обязательны во всём документе).** Любой автоматический индикатор — «сигнал, требующий проверки», не «нарушение», не «коррупция», не «виновен». Допустимые формулировки: «отклонение от планового графика», «требует внимания куратора», «недостаточно данных». Подтверждение этапа на пилоте — **«подтверждение этапа куратором пилота / ответственным лицом»**, а не «официальная государственная приёмка», пока нет НПА или меморандума.

> **MVP не меняется.** Этапы выполнения работ требуют кабинетов, ответственных лиц, статусов, подписей, фотофиксации и аудита → вся эта функциональность относится к **этапу 5 / пилоту с акиматом**. На MVP («читающая версия») этапов работ нет.

> **Конвенция формата.** Изменённые (UC-02, 03, 11, 15, 16, 17, 22, 23, 24, 25, 26, 28, 32, 35) и новые (UC-36…UC-39) сценарии даны в полном формате (≈19 полей). Неизменённые MVP/этап-6 сценарии перенесены компактно с пометкой *«без функциональных изменений»* — это сознательное решение не дублировать рабочий текст.

## 4. Статусные модели

### 4.1. Статус этапа (`project_work_stages.status`)

`draft → planned → in_progress → completed_by_contractor → submitted_for_review → (accepted_by_curator | revision_required | rejected)`; `revision_required → in_progress`.
Сквозные признаки (поверх базового статуса, отдельными полями): `cancelled`, `is_disputed`, `is_overdue`.

| Статус | Описание | Кто переводит |
|---|---|---|
| `draft` | Этап создаётся/редактируется внутри **неутверждённой** версии плана (`draft`/`submitted`/`revision_required`). До утверждения плана этап всегда `draft` | Подрядчик (UC-22) |
| `planned` | Этап в **утверждённой базовой** версии плана (`is_baseline=true`), не начат | Система при утверждении плана (UC-36) |
| `in_progress` | Зафиксирована фактическая дата начала | Подрядчик (UC-23) |
| `completed_by_contractor` | Подрядчик заявил, что работы по этапу завершены (100% + факт. дата) — **ещё не проверено куратором** | Подрядчик (UC-23) |
| `submitted_for_review` | Отправлен куратору на проверку | Подрядчик (UC-25) |
| `revision_required` | Куратор вернул на доработку → возврат в `in_progress` | Куратор (UC-27) |
| `rejected` | Куратор отклонил | Куратор (UC-27) |
| `accepted_by_curator` | Этап подтверждён куратором — **терминальный успешный** | Куратор (UC-26) |
| `cancelled` | Этап отменён (изменение объёма, только через change request UC-37) | Подрядчик/Куратор |

**Сквозные признаки:** `is_overdue` — `planned`/`in_progress`/`completed_by_contractor` и плановая дата завершения в прошлом без приёмки (Система, UC-32); `is_disputed` — открыт спор (UC-34).

> **Однозначность `planned` (правка v4).** До утверждения плана этап существует **только** как `draft`. Статус `planned` появляется исключительно после утверждения базовой версии плана куратором (UC-36). Промежуточного «`planned` в черновике плана» нет.

### 4.2. Статус версии плана (`stage_plan_versions.status`)

`draft → submitted → (approved | revision_required)`; при принятом change request текущая версия → `superseded`, создаётся новая `approved`-версия.

| Статус | Описание | Кто переводит |
|---|---|---|
| `draft` | План создаётся/правится подрядчиком | Подрядчик (UC-22) |
| `submitted` | Отправлен куратору на согласование | Подрядчик (UC-36) |
| `revision_required` | Куратор вернул план на доработку | Куратор (UC-36) |
| `approved` | План утверждён → базовый график (`is_baseline=true`) | Куратор (UC-36) |
| `superseded` | Заменён новой версией после принятого change request | Система (UC-37) |

## 5. Глобальные правила (этап 5)

**R1. Обязательность причины.** Действие не сохраняется без указанной причины/обоснования; причина фиксируется в audit log (UC-31). Обязательна для:
- отклонения этапа (`rejected`) и возврата на доработку (`revision_required`) — UC-27;
- приёмки этапа с обязательным пунктом чек-листа в состоянии `not_ok`/`na` (override) — UC-26;
- параллельного выполнения в обход незавершённой зависимости (`allow_parallel_override=true`) — R4/UC-25/UC-26;
- любого change request, в т.ч. срочного — UC-37;
- отмены этапа (`cancelled`) — UC-23/UC-37;
- отката процента выполнения назад — UC-23.

**R2. SLA реакции куратора.** По каждому ожидающему действию куратора задаётся срок реакции (рабочие дни). При просрочке — сигнал `awaiting_curator_action` («ожидает реакции куратора») куратору и руководителю акимата; подрядчик видит «на рассмотрении N дней». Значения **настраиваемые и согласуются с акиматом**; ориентиры по умолчанию:

| Действие | Ориентир SLA | Поле срока |
|---|---|---|
| Согласование плана этапов (UC-36) | 3 раб. дня | `stage_plan_versions.review_due_at` |
| Проверка этапа на `submitted_for_review` (UC-26/27) | 5 раб. дней | `project_work_stages.review_due_at` |
| Рассмотрение change request (UC-37) | 3 раб. дня | `stage_change_requests.review_due_at` |
| Финальная приёмка проекта (UC-35) | 5 раб. дней | `project.final_review_due_at` |

> SLA-сигнал — операционный, **не обвинительный**: публично показывается только нейтральный факт «этап на проверке с DD.MM», без формулировок о вине куратора. Агрегат «среднее время реакции куратора» — внутренний (антикор/руководитель).

**R3. Утверждаемость плана.** Этап не переходит в `in_progress`, пока версия плана не `approved` (`is_baseline=true`). После утверждения прямое редактирование плана закрыто — только change request (UC-37). (UC-36.)

**R4. Зависимости.** Этап нельзя отправить на проверку, если хотя бы одна обязательная зависимость из `depends_on_stage_ids` не `accepted_by_curator`. Исключение: куратор выставил `allow_parallel_override=true` (R1 — причина обязательна; → сигнал `dependency_override`). Финальная приёмка (UC-35) проверяет завершённость зависимостей для всех `is_required=true`. (UC-25/UC-26/UC-35.)

**R5. Обязательность этапов и фаз фото.** Финальная приёмка доступна только когда все `is_required=true` этапы `accepted_by_curator`. Этап нельзя отправить на проверку без фаз фото из `required_media_phases`. (UC-25/UC-35.)

**R6. Чек-лист приёмки.** Перед `accepted_by_curator` куратор заполняет чек-лист (`stage_acceptance_checklists`). Приёмка разрешена, когда все обязательные пункты = `ok`; иначе — только override с причиной (R1) → сигнал. Типовой чек-лист дороги: фото `before`/`after` есть · геометка внутри объекта · дата съёмки в периоде работ · комментарий подрядчика есть · приложен акт/документ (если требуется) · объём работ указан · замечаний нет/есть. (UC-26.)

**R7. Проверка геометки.** При загрузке медиа с геометкой система считает расстояние до геозоны объекта (PostGIS): внутри полигона → `inside_geozone`; в буфере допуска (настраиваемо, ориентир 100–300 м) → `near_geozone`; дальше → `outside_geozone` (→ сигнал `geo_mismatch`); без геометки → `no_geo` («недостаточно данных»). Это сигнал, требующий проверки, не вывод о фальсификации. (UC-24/UC-32.)

**R8. Модерация медиа.** Перед публикацией медиа обезличивается (размытие лиц и автономеров; ручная проверка спорных кадров). Публикуется (UC-28) только `public_file_ref` при `moderation_status=approved`; оригинал внутренний. (UC-38.)

## 6. Use cases — MVP (читающая версия)

### UC-01. Просмотр карты объектов Астаны *(без функциональных изменений)*
- **Актор:** Гражданин · **Этап:** MVP · **Приоритет:** Высокий
- **Цель:** Увидеть объекты своего района на карте.
- **Основной поток:** карта (MapLibre) с маркерами → приближение → превью → переход в карточку (UC-02). A1. Объект без геопривязки — через поиск (UC-04). E1. Карта не загрузилась → текстовый список района.

### UC-02. Просмотр карточки проекта/контракта *(изменён — расширение этапа 5)*
- **Актор:** Гражданин · **Вторичные:** Система импорта; (этап 5) Подрядчик, Куратор как источники данных этапов
- **Этап:** MVP (база) / Этап 5 (этапы работ) · **Приоритет:** Высокий
- **Цель:** Дать гражданину полную проверяемую картину по контракту; на этапе 5 — публичный прогресс по этапам.
- **Предусловия:** Контракт есть в системе.
- **Триггер:** Переход из карты/поиска/уведомления.

- **Audit log:** просмотр не логируется.
- **Acceptance criteria:** карточка открывается из карты/поиска; ссылка ведёт на первоисточник; флаги помечены; (этап 5) блок этапов показывает план/факт, статус, обезличенное фото и кто подтвердил.
- **Юр./безопасные формулировки:** «сигнал, требующий проверки», «отклонение от планового графика», «этап подтверждён куратором пилота».

### UC-22. Создание плана этапов подрядчиком *(изменён — версия плана и новые поля)*

- **Audit log:** создание плана/этапов, версия (UC-31).

- **Юр./безопасные формулировки:** «плановый график работ»; без утверждений об обязательности перед третьими лицами.

### UC-23. Обновление фактического прогресса этапа *(изменён — completed_by_contractor, R3)*
- **Актор:** Подрядчик · **Вторичные:** Представитель подрядчика
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Фиксировать фактический ход работ.
- **Предусловия:** Этап `planned`/`in_progress`/`revision_required`; **план утверждён (R3)**.
- **Основной поток:**
  1. Фиксация факт. даты начала → `in_progress` (доступно только при утверждённом плане).
  2. Обновление процента и комментария.
  3. По завершении работ — факт. дата завершения и 100% → `completed_by_contractor` (ждёт отправки на проверку).
- **Альтернативы:** A1. Прикрепление связанных документов/актов.
- **Исключения:** E1. Плановая дата завершения в прошлом без приёмки → `is_overdue=true` (UC-32). E2. Откат процента назад → причина обязательна (R1).
- **Постусловия:** Прогресс обновлён; пересчитываются сигналы (UC-32) и при необходимости рейтинг (UC-33).
- **Данные/поля:** `stage_updates`; обновление `project_work_stages` (actual_start/actual_end/progress_percent/status).
- **Права доступа:** только подрядчик/представитель своего проекта.
- **Audit log:** изменённые поля (old→new), причина, версия (UC-31).
- **Acceptance criteria:** `in_progress` недоступен без утверждённого плана; 100% переводит в `completed_by_contractor`; просрочка вычисляется автоматически; откат прогресса требует причины.
- **Юр./безопасные формулировки:** «отклонение от планового графика», «недостаточно данных».

### UC-24. Фото/видео фиксация этапа с геометкой *(изменён — геопроверка R7, модерация R8)*
- **Актор:** Подрядчик · **Вторичные:** Представитель подрядчика, Модератор

- **Цель:** Подтвердить ход работ фотофиксацией «до/в процессе/после» с геометкой.
- **Основной поток:**

- **Acceptance criteria:** поддерживаются фазы; геометка проверяется и сохраняется; отсутствие/несоответствие геометки помечается; публикуется только обезличенный кадр; хеш фиксируется для контроля дублей (UC-32).

### UC-26. Приёмка этапа куратором *(изменён — чек-лист R6, статусы, R1)*
- **Актор:** Куратор акимата · **Вторичные:** Руководитель акимата, Подрядчик
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Подтвердить выполнение этапа (этапное подтверждение в системе).
- **Предусловия:** Этап `submitted_for_review`; куратор назначен (UC-39).
- **Основной поток:**
  1. Куратор изучает прогресс, обезличенную фотофиксацию (вкл. `geo_match_status`), план/факт.

  3. Решение «принять» (все обязательные пункты `ok`) → этап `accepted_by_curator`.

- **Альтернативы:** A1. Принять с обязательным пунктом `not_ok`/`na` → только с причиной (R1) → сигнал. A2. Принять с замечанием. A3. ЭЦП/ЭҚҚ при интеграции.

- **Постусловия:** Этап подтверждён; обновляются статус проекта (§4.3), сигналы (UC-32), рейтинг (UC-33); таймер SLA закрыт.
- **Данные/поля:** `stage_reviews` (decision=accepted, reviewed_at, remarks, is_final=false), `stage_review_checklist_results`, `stage_signatures` (signer_fio/position/org, signed_at, signature_type, ip, user_agent).
- **Права доступа:** принимает только назначенный куратор; публично — ФИО/должность/организация/дата; IP/user-agent — только audit/админ.
- **Уведомления:** подрядчику — «этап подтверждён» → UC-30.
- **Audit log:** решение, чек-лист, подписант, дата, версия (UC-31, неизменяемо).
- **Acceptance criteria:** приёмка требует заполненного чек-листа; приёмка при `not_ok` обязательного пункта — только с причиной и порождает сигнал; фиксирует ФИО/должность/организацию/дату; нет формулировки «государственный акт».
- **Юр./безопасные формулировки:** **«этап подтверждён куратором пилота / ответственным лицом»**.

### UC-36. Согласование плана этапов куратором
- **Актор:** Куратор акимата · **Вторичные:** Подрядчик, Руководитель акимата
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Сделать план этапов утверждаемым базовым графиком до старта работ.
- **Предусловия:** Подрядчик создал план (UC-22), версия `draft`; куратор назначен (UC-39).
- **Триггер:** Подрядчик отправляет план на согласование; устанавливается `review_due_at` (SLA R2).
- **Основной поток:**
  1. Версия плана → `submitted`.
  2. Куратор просматривает состав этапов, обязательность, зависимости, плановые сроки.
  3. **Утверждает** → `approved`, `is_baseline=true`; этапы → `planned`; проект → `planned`. Либо **возвращает** → `revision_required` (план редактируется подрядчиком). Возврат требует причины (R1).
  4. После утверждения изменения — только через change request (UC-37, R3).
- **Альтернативы:** A1. Несколько циклов доработки (счётчик → сигнал `frequent_plan_changes`). A2. ЭЦП/ЭҚҚ.
- **Исключения:** E1. Нет назначенного куратора → «ожидает назначения куратора», уведомление руководителю (UC-39). E2. Пустой план или дата завершения раньше начала → утверждение недоступно. E3. SLA-просрочка согласования → сигнал `awaiting_curator_action` (R2).
- **Постусловия:** Существует одна базовая утверждённая версия плана; этапы можно начинать.
- **Данные/поля:** `stage_plan_versions` (status, is_baseline, approved_by, approved_at, review_due_at), `project_work_stages.status`, `curator_assignments`.
- **Права доступа:** утверждает только назначенный куратор/руководитель; публично — факт утверждения, версия, подписант, дата.
- **Уведомления:** подрядчику — «план утверждён / возвращён на доработку» → UC-30.
- **Audit log:** отправка, решение, причина возврата, подписант, версия (UC-31).
- **Acceptance criteria:** этап не переходит в `in_progress` без утверждённого базового плана; утверждение фиксирует подписанта; после утверждения прямое редактирование закрыто; возврат требует причины.
- **Юр./безопасные формулировки:** «согласование плана куратором пилота», «базовый плановый график»; не «государственное утверждение».

### UC-37. Запрос на изменение утверждённого плана этапов (change request)
- **Актор:** Подрядчик · **Вторичные:** Куратор акимата
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Контролируемый прослеживаемый механизм изменения базового плана.
- **Предусловия:** Есть утверждённая базовая версия плана (UC-36); этап не в финальной приёмке.
- **Основной поток:**
  1. Подрядчик создаёт change request: `request_type`, `payload` (old→new), **обязательная причина (R1)**.
  2. Запрос → `submitted`; устанавливается `review_due_at` (SLA R2); уходит куратору.
  3. Куратор **утверждает** → новая версия плана (`version+1`, `approved`, `is_baseline=true`), прежняя → `superseded`, запрос → `approved`. Либо **отклоняет** (с причиной R1) → план без изменений, запрос → `rejected`.
- **Альтернативы:** A1. Батч из нескольких изменений. A2. Срочное изменение по согласованию с руководителем (причина обязательна, R1).
- **Исключения:** E1. Причина не указана → запрос не сохраняется (R1). E2. Изменение даты задним числом (раньше зафиксированного факта) → блок/сигнал. E3. SLA-просрочка рассмотрения → сигнал `awaiting_curator_action`.
- **Постусловия:** История версий плана сохранена; сравнение версий доступно.
- **Данные/поля:** `stage_change_requests`, `stage_plan_versions` (новая версия), `project_work_stages` (правки по payload).
- **Права доступа:** инициирует подрядчик; утверждает назначенный куратор; публично — факт изменения, тип, кто утвердил.
- **Уведомления:** сторонам — открытие/решение по запросу → UC-30.
- **Audit log:** запрос, payload (old→new), причина, решение, новая версия (UC-31).
- **Acceptance criteria:** базовый план не меняется в обход change request; каждая правка создаёт новую версию с сохранением предыдущей; изменение задним числом блокируется/порождает сигнал; причина обязательна.
- **Юр./безопасные формулировки:** «запрос на изменение плана», «версия графика».

### UC-38. Модерация и обезличивание медиа
- **Актор:** Система (авто) / Модератор · **Вторичные:** Подрядчик, Куратор
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Не допустить публикацию ПД третьих лиц и чувствительного контента на фотофиксации.
- **Предусловия:** Загружено медиа этапа (UC-24); `moderation_status=pending`.
- **Основной поток:**
  1. Авто-обработка: детекция и размытие лиц и автономеров → формируется `public_file_ref`; `moderation_status=auto_processed`.
  2. Кейсы риска (прохожие, частная территория, служебные документы, низкая уверенность детекции) → `manual_review`.
  3. Модератор подтверждает/правит → `approved`, либо отклоняет → `rejected`.
  4. В публичный прогресс (UC-28) попадает только `public_file_ref` при `approved`.
- **Альтернативы:** A1. Подрядчик повторно загружает корректный кадр. A2. Полное скрытие при невозможности обезличить (этап «недостаточно данных»).
- **Исключения:** E1. Авто-детекция недоступна → всё медиа в `manual_review` (fail-safe, не публикуется). E2. Видео без покадрового обезличивания → не публикуется автоматически.
- **Постусловия:** Публикуется только обезличенный проверенный материал; оригинал внутренний.
- **Данные/поля:** `stage_media` (moderation_status, public_file_ref, moderated_by, moderated_at, geo_match_status).
- **Права доступа:** оригинал — подрядчик/куратор/модератор; публично — только `public_file_ref` (approved); решения модерации — внутренние.
- **Уведомления:** подрядчику — «медиа отклонено, нужна замена» → UC-30.
- **Audit log:** статус модерации, кто/когда, причина (UC-31).
- **Acceptance criteria:** ни одно медиа не публикуется со статусом ≠ `approved`; лица и номера размыты до публикации; при отказе детекции — ручная проверка, не публикация; оригинал недоступен публично.
- **Юр./безопасные формулировки:** «обезличивание», «защита ПД третьих лиц» (ст. 17 № 94-V).

### UC-39. Назначение куратора на проект
- **Актор:** Руководитель акимата / Администратор системы · **Вторичные:** Куратор, Подрядчик
- **Этап:** 5 · **Приоритет:** Высокий
- **Цель:** Зафиксировать, кто и с какими полномочиями курирует проект, чтобы был источник «назначенного куратора» для UC-25/26/27/35/36.
- **Предусловия:** Кабинет акимата (UC-15); есть проект пилота; пользователь имеет роль руководителя/админа.
- **Триггер:** Руководитель/админ открывает проект и назначает куратора.
- **Основной поток:**
  1. Выбор проекта и куратора (из пользователей акимата).
  2. Указание роли (`curator`/`supervisor`), срока действия (`valid_from`/`valid_to`).
  3. Сохранение → куратор получает доступ к объекту и его очереди проверки (UC-29).
- **Альтернативы:** A1. Переназначение/замена куратора (старое назначение закрывается `valid_to`, открывается новое). A2. Несколько кураторов на проект (например, по направлениям).
- **Исключения:** E1. Пользователь не относится к управлению проекта → назначение запрещено. E2. Перекрытие сроков активных назначений одной роли → предупреждение/запрет.
- **Постусловия:** Существует активное назначение куратора; UC-25/26/27/35/36 имеют «назначенного куратора».
- **Данные/поля:** `curator_assignments` (project_id, curator_id, role, assigned_by, valid_from, valid_to).
- **Права доступа:** назначает руководитель акимата/админ; куратор не назначает себя; публично — косвенно (ФИО/должность подтвердившего при приёмке).
- **Уведомления:** куратору — «вы назначены на проект»; подрядчику (опц.) — «по проекту назначен куратор» → UC-30.
- **Audit log:** назначение/переназначение/снятие, кто, когда, срок (UC-31).
- **Acceptance criteria:** без активного назначения этап не уходит конкретному куратору (UC-25 E1); назначение фиксирует роль и срок; переназначение сохраняет историю; самоназначение невозможно.
- **Юр./безопасные формулировки:** «назначение ответственного куратора пилота»; роль — организационная, не «государственное должностное назначение».

## 8. Use cases — Этап 6 (AI, антикор, API)

### UC-18. Рекомендации AI-советника *(изменён — анализ просрочек этапов)*
- **Актор:** Все роли · **Этап:** 6 · **Приоритет:** Средний
- **Основной поток:** AI формирует рекомендацию по роли на KZ/RU со ссылками на первичные данные. A1. Акимату — «отставание этапов + параллельные отстающие контракты → риск срыва, рекомендуется проверка». A2. Подрядчику — причина просадки рейтинга по этапам. A3. Гражданину — напоминание по дефект-репорту. E1. Недостаточно данных → рекомендация не выдаётся.
- **Данные/поля:** агрегаты этапов/сигналов; **только публичные/обезличенные данные передаются во внешний API**.
- **Acceptance criteria:** каждая рекомендация имеет ссылки на данные; AI не блокирует и не инициирует проверки; ПД во внешний API не передаются.
- **Юр./безопасные формулировки:** **«AI советует — человек решает»**.

### UC-19. Авто-резюме сигналов для антикора *(изменён — паттерны по этапам)*
- **Актор:** Антикоррупционный аналитик · **Этап:** 6 · **Приоритет:** Средний
- **Основной поток:** совокупность независимых сигналов на одном экране, включая паттерны по этапам (повторяющиеся просрочки, резкие изменения сроков/плана, одинаковые фото, этапы без фото, приёмки задним числом, геометки вне объекта, много отклонений у подрядчика, один куратор принимает много спорных) → приоритет проверки со ссылками на первичные данные и audit log. A1. Экспорт. E1. Единичный слабый сигнал → не эскалируется.
- **Права доступа:** только антикор/госорган; **не публично** (особенно паттерны по куратору).
- **Acceptance criteria:** сводка собирает сигналы по подрядчику/проекту/куратору; каждый пункт ведёт к первичным данным; паттерны по куратору закрыты от публики.
- **Юр./безопасные формулировки:** «совокупность сигналов, требующих проверки».

### UC-20. Доступ через публичный API *(без функциональных изменений)*
- **Актор:** Журналист / исследователь / банк · **Этап:** 5–6 · **Приоритет:** Низкий
- **Основной поток:** выдача данных/отчётов, троттлинг. A1. Готовые отчёты вместо сырого API. **Постусловие:** ПД граждан не раскрываются (агрегаты/юрлица); прогресс по этапам — публичное подмножество (обезличенные медиа).

## 9. Модель данных для этапов работ

> *Допущение:* конкретные типы полей и индексы определяются на этапе проектирования БД; ниже — логическая модель. PostGIS используется для геометок (`geo_point`) и геопроверки (R7).

### 9.1. `project_work_stages` — этапы работ
- **Поля:** `id`, `project_id` (FK), `parent_stage_id` (FK self, nullable), `template_item_id` (nullable), `plan_version_id` (FK → `stage_plan_versions`), `title`, `description`, `planned_start`, `planned_end`, `actual_start`, `actual_end`, `status` (§4.1), `progress_percent`, `order_index`, `geo_point`, `contractor_comment`, `is_required` (bool, default true), `required_media_phases` (array enum before/in_progress/after), `depends_on_stage_ids` (array FK self), `allow_parallel_override` (bool, default false), `acceptance_checklist_id` (FK, nullable), `review_due_at` (SLA, nullable), `is_overdue`, `is_disputed`, `created_by`, `created_at`, `updated_at`, `version`.
- **Создаёт:** Подрядчик (UC-22, статус `draft`). **Статус:** меняется системой/куратором по решениям (UC-26/27/36).
- **Публично:** `title`, план/факт даты, `status`, `progress_percent`, `is_overdue`, `is_disputed`, геометка (в допустимой точности). **Скрыто:** `draft`-этапы, закрытые комментарии.

### 9.2. `stage_plan_versions` — версии плана *(новая)*
- **Поля:** `id`, `project_id` (FK), `version` (int), `status` (§4.2), `is_baseline` (bool), `created_by`, `created_at`, `submitted_at`, `review_due_at` (SLA), `approved_by` (FK curator, nullable), `approved_at`, `change_summary` (text, nullable).
- **Создаёт:** Подрядчик (черновик). **Утверждает:** Куратор (UC-36).
- **Публично:** факт «план утверждён», `version`, `approved_by`, `approved_at`. **Скрыто:** черновики.

### 9.3. `stage_change_requests` — запросы на изменение плана *(новая)*
- **Поля:** `id`, `project_id` (FK), `plan_version_id` (FK), `request_type` (enum shift_dates/add_stage/remove_stage/change_required_flag/reorder/split_stage), `payload` (jsonb old→new), `reason` (text, обязателен R1), `status` (submitted/approved/rejected), `requested_by`, `review_due_at` (SLA), `reviewed_by` (FK curator, nullable), `reviewed_at`, `created_at`.
- **Создаёт:** Подрядчик (UC-37). **Решает:** Куратор.
- **Публично:** факт изменения, тип, кто утвердил. **Скрыто:** внутренние комментарии.

### 9.4. `stage_templates` — шаблоны этапов
- **Поля:** `id`, `name`, `project_type` (road/water/landscaping/school_hospital/custom), `is_system`, `owner_id` (nullable), `created_by`, `created_at`, `version`.
- **Публично:** состав системных шаблонов. **Скрыто:** пользовательские — только владельцу.

### 9.5. `stage_template_items` — элементы шаблона *(+обязательность/зависимости/чек-лист)*
- **Поля:** `id`, `template_id` (FK), `parent_item_id` (self, nullable), `title`, `default_description`, `default_duration_days`, `order_index`, `is_required` (bool, default true), `required_media_phases` (array enum), `depends_on_item_order` (array int), `default_acceptance_checklist` (jsonb).
- **Создаёт/изменяет:** вместе с шаблоном (UC-21).

### 9.6. `stage_updates` — обновления прогресса
- **Поля:** `id`, `stage_id` (FK), `update_type` (progress/start/finish/comment), `progress_percent`, `actual_date`, `comment`, `reason` (для отката, R1), `created_by`, `created_at`.
- **Создаёт:** Подрядчик (UC-23). Не редактируется (история).

### 9.7. `stage_media` — фото/видео *(+геопроверка, модерация)*
- **Поля:** `id`, `stage_id` (FK), `media_type` (photo/video), `phase` (before/in_progress/after), `file_ref` (оригинал, внутр.), `public_file_ref` (обезличенная версия), `geo_point`, `geo_match_status` (inside_geozone/near_geozone/outside_geozone/no_geo), `geo_distance_m` (nullable), `captured_at`, `uploaded_by`, `hash`, `moderation_status` (pending/auto_processed/manual_review/approved/rejected), `moderated_by` (nullable), `moderated_at` (nullable), `created_at`.
- **Создаёт:** Подрядчик (UC-24); модерация — UC-38. **Публично:** только `public_file_ref` (approved) и фаза. **Скрыто:** оригинал, метаданные, `hash`.

### 9.8. `stage_reviews` — проверки куратора
- **Поля:** `id`, `stage_id` (FK), `reviewer_id` (FK curator), `decision` (accepted/rejected/revision_required), `comment`, `remarks`, `reason` (обязателен для rejected/revision/override, R1), `reviewed_at`, `is_final` (этапная vs финальная), `created_at`.
- **Создаёт:** Куратор (UC-26/27/35). Не редактируется (новые записи).
- **Публично:** `decision`, `reviewed_at`, кто подтвердил. **Скрыто:** закрытые `remarks`/`comment`.

### 9.9. `stage_acceptance_checklists` — чек-листы приёмки *(новая)*
- **Поля:** `id`, `stage_id` (FK, nullable) или `project_type`, `items` (jsonb: список `{key, label, is_required, source}`), `created_from_template_id` (nullable).

### 9.10. `stage_review_checklist_results` — заполнение чек-листа *(новая)*
- **Поля:** `id`, `review_id` (FK → `stage_reviews`), `checklist_item_key`, `result` (ok/not_ok/na), `comment`.
- **Создаёт:** Куратор при приёмке (UC-26). **Публично:** агрегат «замечаний нет/есть»; детали — по политике.

### 9.11. `stage_signatures` — подтверждения/подписи
- **Поля:** `id`, `stage_id` (FK), `review_id` (FK), `signer_fio`, `signer_position`, `signer_org`, `signed_at`, `signature_type` (system_mark/ecp), `ip`, `user_agent`, `created_at`.
- **Публично:** `signer_fio`, `signer_position`, `signer_org`, `signed_at` (служебные данные). **Скрыто:** `ip`, `user_agent`.
- **Формулировка:** «подтверждение этапа куратором пилота», не «государственный акт».

### 9.12. `stage_audit_log` — неизменяемый журнал
- **Поля:** `id`, `entity_type`, `entity_id`, `action`, `actor_id`, `actor_role`, `changed_fields` (old→new), `reason` (R1), `timestamp`, `version`, `ip`, `user_agent`.
- **Создаёт:** Система (append-only). **Изменяет:** никто (immutable). **Публично:** нет (чтение — админ/госорган/антикор).

### 9.13. `stage_risk_signals` — риск-сигналы
- **Поля:** `id`, `signal_type` (stage_overdue/frequent_revisions/plan_fact_deviation/no_media/accepted_without_review/contractor_frequent_delays/curator_backdated_acceptance/duplicate_media/**geo_mismatch**/**frequent_plan_changes**/**dependency_override**/**awaiting_curator_action**), `stage_id` (nullable), `contractor_bin` (nullable), `curator_id` (nullable), `severity`, `detected_at`, `status` (active/cleared), `evidence_refs`, `created_at`.
- **Создаёт:** Система (UC-32). **Публично:** сигналы по объекту (просрочка, отклонение, гео, SLA-нейтрально). **Скрыто:** паттерны по подрядчику/куратору.

### 9.14. `curator_assignments` — назначения кураторов
- **Поля:** `id`, `project_id` (FK), `curator_id` (FK), `assigned_by`, `role` (curator/supervisor), `valid_from`, `valid_to`, `created_at`.
- **Создаёт/изменяет:** Руководитель акимата / Администратор (UC-39).
- **Публично:** косвенно (подписант при приёмке). **Скрыто:** внутренняя матрица назначений.

## 13. Acceptance criteria — MVP и этап 5

### 13.1. MVP (читающая версия)
- Кабинетов этапов **нет**; контур ПД отсутствует.
- Доступны: публичная карта, карточки, 4 флага, Telegram-подписки, импорт, нормализация, геопривязка.
- Карточка проекта (UC-02) показывает только импортированные данные + ссылку на goszakup; блок этапов скрыт.
- Go/No-Go-гейт геопривязки ≥70% (UC-10) пройден.

### 13.2. Этап 5 (пилот с акиматом)
- Руководитель акимата назначает куратора на проект (UC-39); без активного назначения этап не уходит конкретному куратору.
- Подрядчик создаёт план этапов (UC-22), отправляет на согласование; **план утверждается и версионируется** куратором (UC-36); до утверждения этапы только `draft`.
- Этап не стартует (`in_progress`) без утверждённого базового плана (R3); 100% переводит в `completed_by_contractor`.
- Отправка на проверку проверяет обязательные фазы фото (R5) и завершённость зависимостей (R4).
- Перед приёмкой куратор заполняет чек-лист (R6); приёмка при незакрытом обязательном пункте — только с причиной (R1) и порождает сигнал.
- Изменения утверждённого плана идут только через change request с сохранением истории версий (UC-37).
- Медиа публикуется только обезличенным и проверенным (UC-38); геометка вне геозоны → сигнал `geo_mismatch` (R7).
- Каждое решение об отклонении/возврате/override/отмене/change request сопровождается обязательной причиной (R1).
- По действиям куратора действуют SLA; просрочка → сигнал `awaiting_curator_action` (R2).
- Audit log этапов работает и неизменяем (UC-31); просрочки и отклонения считаются автоматически (UC-32); этапы влияют на рейтинг по объективным компонентам (UC-33).
- **Финальная приёмка возможна только после завершения всех обязательных этапов и их зависимостей** (UC-35, R4/R5).
- Подтверждения оформлены как «подтверждение этапа куратором пилота», не «государственный акт» (без НПА/меморандума).

## 15. Итог

**Что покрыто полностью**
- Вся MVP-функциональность (UC-01…UC-11) — читающая версия не изменена.
- Полный цикл этапного контроля: назначение куратора → план → согласование → выполнение → фото/геометка → проверка по чек-листу → change request → финальная приёмка → рейтинг.
- Модель данных, матрица доступа, публичность, уведомления, статусные модели, SLA и acceptance criteria даны на уровне, пригодном для разработки.

**Что добавлено в v4 против v3.1**
- UC-39 «Назначение куратора»; SLA реакции куратора (R2) и сигнал `awaiting_curator_action`; единое правило обязательной причины (R1); уточнение статуса `planned` (только после утверждения плана); патчи v3.1 применены прямо в тексте UC.

**Открытые вопросы (юрист)**
- Правовой статус «подтверждения этапа» и «согласования плана» на пилоте; формулировки в публичной части.
- Достаточность авто-размытия лиц/номеров как меры обезличивания (№ 94-V); хранение оригинала медиа и срок.
- Публикация ФИО/должности подписанта без отдельного согласия (служебная информация).
- Допустимая точность публичной геометки и буфер `near_geozone`.
- Хранение IP/user-agent в подписи и audit log как ПД.

**Открытые вопросы (акимат)**
- Перечень обязательных этапов и типовые чек-листы приёмки по типам проектов — *в документах не указаны*.
- Конкретные значения SLA реакции куратора.
- Кто выступает куратором и модератором медиа; регламент рассмотрения change request.
- Согласие на публичное отображение факта подтверждения этапа и данных подписанта.
- Готовность вести и согласовывать этапы в системе на пилоте без официального НПА.

**Вне MVP**
- Весь блок этапов работ (UC-21…UC-39) — этап 5.
- Кабинеты, верификация, оценки, дефект-репорты — этап 5.
- AI-анализ этапов, антикор-паттерны, публичный API, аффилированность — этап 6.
