# Предполётные решения (Story 0.4)

> **Назначение:** зафиксировать критические инварианты ДО первого живого импорта, чтобы они не
> «изобретались по месту» и не всплывали позже как обратные зависимости (architecture.md:443). Многие
> решения УЖЕ реализованы кодом — этот документ их **формализует** и ссылается на реализацию, а не
> переизобретает. Соседи: `stage0-access.md` (Story 0.1, §6 потолок парсера), `interim-scrape-bridge.md`
> (трек «Парсер-мост»), `stage0-verdict-*.json` (Story 0.2, артефакт гейта №0).

## 1. Ключ идемпотентности импорта (AC1)

**Решение:** дедуп/UPSERT-ключ = **`(source, goszakup_<entity>_id)`** — стабильный **бизнес-ключ**, НЕ
суррогатный PK.

- **`snapshot_id` НЕ входит в уникальность.** Снапшот — измерение во времени, а не идентичность сущности;
  включение его в ключ плодило бы дубли при каждом импорте. [Source: architecture.md:877–878, AR-8]
- **Почему natural, не суррогат:** `goszakup_<entity>_id` стабилен между ре-импортами (суррогатный
  identity-PK — нет). Компонент `source` разделяет источники (`ows | file | scrape`) → переживает swap
  трека «Парсер-мост» (scrape→ows) без коллизий. [Source: architecture.md:526, 580; epics.md:708–710]
- **Применяется ко ВСЕМ сущностям** при наполнении в Epic 2: `contracts` (`goszakup_contract_id`),
  `announcements`/`trd_buy` (`goszakup_id`), `lots` (`goszakup_lot_id`), `acts` (`goszakup_act_id`),
  `rnu_entries` (`goszakup_rnu_id`). [Source: data_model §1]

**Реализованный прецедент (Story 2.0 — уже в коде):**
- `migrations/0003_projection_lots.sql` — `goszakup_lot_id TEXT NOT NULL UNIQUE`.
- `server/internal/store/queries/lots.sql` — `UpsertLot ... ON CONFLICT (goszakup_lot_id) DO UPDATE`
  (идемпотентно; повтор не плодит дубли).
- `migrations/0004_interim_geo_lots.sql` (Story 0.7) — то же правило связи по стабильному
  `goszakup_lot_id` (без hard FK к проекции — кураторская ⊥ проекционная, AR-4).

> **Для Epic 2 (живой импорт):** UPSERT по `(source, goszakup_<entity>_id)`; `snapshot_id` — отдельное
> поле-измерение, НЕ в `UNIQUE`/`ON CONFLICT`. Атомарная публикация снапшота — Story 2.4.

## 2. Частичный Go (`go_with_fallback`) — правило и провенанс (AC2)

**Правило:** при автогеопривязке `geo_coverage < 0.70` (Гейт №0, Story 0.2/0.3) доступен **осознанный
частичный Go** — НЕ автоматически, только через явный флаг `-allow-fallback` + **sign-off владельца**.

- **Стоимость частичного Go — известная, не «магия»:** недостающая геопривязка добивается **ручной
  гео-очередью через Directus** (FR-5) до целевого покрытия. Это зафиксированная цена решения, а не
  скрытый риск. [Source: epics.md:426, 544; architecture.md:170]
- **Sign-off обязателен и машинно-доказуем.** Артефакт `go_with_fallback` несёт блок `provenance`
  (`owner`, `date`, `reason`, опц. `checkpoint`) — кто/когда/почему подписал. **Неподписанный частичный Go
  недопустим:** `-allow-fallback` без `-fallback-owner`+`-fallback-reason` → `stage0-audit` падает
  fail-fast (exit 2), артефакт не выпускается. Закрывает defer ревью Story 0.2 («baseline должен быть
  машинно-доказуем, а не на факте передачи флага»).
- **Владелец риска и дата контрольной точки** назначаются при **фактическом** частичном Go — это требует
  живых данных Гейта №0 (Story 0.3, токен-блокирована). До реального прогона `go_with_fallback` не
  выпускается; механизм провенанса (флаги/поля/fail-fast) готов (Story 0.4). Плейсхолдер в провенансе
  недопустим (честность: подпись — реальная или её нет).
- **Связь с серверным гейтом:** на работающем приложении автопокрытие гейтит per-район `geo_coverage`
  (Epic 3, Story 3.3, `<0.70 → фолбэк-режим`). Гейт №0 (0.2/0.3) — предполётный замер до коммитов.

**Реализация (Story 0.4 — уже в коде):**
- `stage0-audit/verdict.go` — `Provenance{owner,date,reason,checkpoint}`, поле `Verdict.provenance`
  (`omitempty`: только у `go_with_fallback`); населяется в ветке `-allow-fallback`.
- `stage0-audit/main.go` — флаги `-fallback-owner`/`-fallback-reason`/`-fallback-checkpoint`; хелпер
  `requireFallbackSignoff` (fail-fast exit 2 при неподписанном fallback).
- `methodology_version` **не растёт** (`stage0-1.0`): провенанс — аддитивная метаданность, формула
  вердикта и пороги не меняются; enforcement подписи — операционный fail-fast в `main()`, `deriveVerdict`
  остаётся чистой. [Source: verdict.go:8–12 — версия пинит «формулу + пороги»]

**Запуск (пример подписанного частичного Go):**
```bash
cd stage0-audit
go run . -source file -data-dir ./data -geocoder nominatim -geo-sample 200 \
  -format json -allow-fallback \
  -fallback-owner "<владелец риска>" \
  -fallback-reason "ручная гео-очередь Directus (FR-5) как известная стоимость" \
  -fallback-checkpoint 2026-09-01
```

## 3. Демо-стратегия: 3 гео-независимых контракта-истории (AC3)

**Решение (Issues #6):** демо-фундамент = **3 ручных гео-независимых контракта-истории**, стоящих при
**любом** проценте автогеопривязки. [Source: architecture.md:339, 897–900; epics.md:451, 546, 716–718]

**Ответ на вопрос жюри «какое демо выигрывает при автогео 45%?»:** демо **не зависит** от % автогео —
читаемые карточки контрактов + экран методики флага работают на **ручных** данных (geo-независимый
вертикальный срез). Карта с реальными точками — приятный бонус сверху, не несущая ось демо. Первый WOW —
на 2–3 неделе, до закрытия гейта геопокрытия.

**Реализованный выбор (Story 1.9 — уже в коде):**
- `DEMO-0001`, `DEMO-0002`, `DEMO-0003` — 3 контракта-истории, синтетический seed
  `fixtures/seed/contracts.sql`.
- Сквозной вертикальный срез: карточка контракта → методика флага → первоисточник (Story 1.7/1.9).
- `DEMO-0004` — намеренно негеокодированный (демонстрирует честное «без точки на карте», AC3 Story 1.8).

> Демо-фундамент **самодостаточен на синтетике** и не блокируется токеном/гейтом — снимает риск «нет WOW,
> пока не закрыт гейт».

## 4. Снапшот схемы ows_v2 (B-1) — процедура + дескоуп на токен (AC4)

**Процедура захвата** (когда токен получен — Story 0.1):
1. Запросить реальный ответ каждого ресурса ows_v2 (`contract`, `lots`, `trd-buy`, `subject`, `rnu`,
   `acts`, `journal`) живым токеном.
2. Сохранить как `fixtures/ows_v2/<resource>.json` (записанный ответ) — golden-вход для границы декода.
3. Сгенерировать `fixtures/ows_v2/<resource>_schema_hash.txt` через существующий механизм
   `decode.SchemaHash` (Story 1.10/2.0) — хеш по НАБОРУ полей; `decode` стопает импорт при дрейфе
   зафиксированной схемы (detect-and-halt, не тихий 0). [Source: architecture.md:214, 344, 715, 725]
4. Закоммитить как версионируемый контракт схемы (как `stage0-verdict-*.json` для гейта).

**Дескоуп (честность над домыслом):** реальный снапшот требует **живой ответ ows_v2 → токен** (Story
0.1/0.3). Фейковый ows_v2-ответ НЕ выдумывается (гардрейл честности). **AC4 закрыт на уровне «процедура
задокументирована + критерий закрытия = токен получен».** Плейсхолдеры `fixtures/ows_v2/.gitkeep` и
`docs/api-contracts/ows_v2/.gitkeep` уже на месте; механизм `decode.SchemaHash` уже реализован — недостаёт
только реального ответа.

**Критерий закрытия AC4:** получен `GOSZAKUP_TOKEN` (Story 0.1) → выполнить процедуру выше → закоммитить
`fixtures/ows_v2/*` + `*_schema_hash.txt`.
