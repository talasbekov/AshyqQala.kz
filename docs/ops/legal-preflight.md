## 1. Правовая основа, ToS ows_v2, мониторинг НПА, хранение снапшотов (AC1)

### 1.1 Правовая основа (позитивная опора)

Платформа реализует право граждан, а не нарушает его:

- **Официальный канал, не парсинг.** Данные берутся из унифицированных сервисов открытых данных goszakup
  (`ows_v2`, REST по токену из профиля участника) — это принципиально для юр-чистоты (несущий принцип §6.1/§6.4).
- **Закон РК «О доступе к информации»** закрепляет открытость данных о расходовании бюджетных средств.
- **Сведения о юрлицах** (БИН, наименование, история контрактов) — **не персональные данные физлиц**.

[Source: конкурсный §6.1 (правовая основа); PRD §7.1 (позитивная правовая опора), глоссарий «БИН — не ПД»; architecture.md:94–96]

### 1.2 Ответственный за мониторинг НПА 👤

Правила использования единой платформы закупок периодически меняются приказами Минфина (прецеденты:
№ 783 от 17.12.2025, № 102 от 13.02.2026 — [Source: конкурсный §6.4:337]) — за этим нужен назначенный человек.

- **Роль:** ответственный за юридический контур / мониторинг НПА (приказы Минфина, условия ows_v2).
- **Требование:** отслеживать изменения правил использования ows_v2 и профильных НПА; при смене схемы/условий —
  инициировать реакцию (стоп импорта + алерт — FR-3; пересмотр допустимости).
- **👤 Открытый пункт (решение владельца):** реальное имя/должность ответственного **назначается владельцем**.
  Здесь оно **не выдумывается** (честность: подпись/назначение — реальное или его нет; прецедент 0.4 — владелец/дата
  не фабрикуются). Зафиксировать имя при назначении — без изменения остального документа.

[Source: конкурсный §6.4 (юр-риски, НПА-мониторинг); PRD §8 (назначить ответственного за мониторинг НПА), §13 (риск смены схемы); docs/ops/stage0-access.md §1 (владелец/ротация токена)]

### 1.3 Хранение и ре-публикация снапшотов ows_v2

- **Ориентир (предварительно, не окончательный вывод):** хранение и ре-публикация снапшотов ответа ows_v2
  (иммутабельный снапшот-стор + производная БД-выдача) **предположительно укладываются** в модель «официальный
  открытый канал» — платформа публикует уже открытые данные из официального источника. Это **согласуется** с
  юр-гейтом архитектуры «ToS источника → хранение/ре-публикация снапшотов не нарушает условия API» — но **на
  уровне ориентира**, а не подтверждённого факта. [Source: architecture.md:176, 104–117 (снапшот как фундамент)]
- **👤 Гейт «ДО живого импорта» (финальная сверка):** окончательное подтверждение «не нарушает условия API»
  требует сверки с **живым текстом ToS** ows_v2 (профиль участника goszakup) и, при сомнении, консультации
  юриста. Эта сверка должна быть выполнена назначенным ответственным (§1.2) **до первого живого импорта**
  (публикации снапшотов) — **симметрично** гейту «до публичного запуска бота» для `telegram_chat_id` (§3). До
  сверки соответствие зафиксировано лишь **как ориентир** и **не выдаётся за окончательный юр-факт**.

## 2. Публикуемые поля и отсутствие ПД физлиц (AC2)

**Вывод:** публичный слой MVP содержит **только сведения о юрлицах и служебную информацию должностных лиц**.
Персональные данные физлиц-граждан **отсутствуют** (нет аккаунтов, народных оценок, ИИН — это этап 5, PRD §10/§11.2).

| Сущность | Публикуемые поля | Класс данных |
|---|---|---|
| `organizations` | `bin`, `name_ru`, `name_kk`, `reg_kato`, `is_customer`, `is_supplier`, `source_url` | Юрлица (БИН — **не ПД физлица**) |
| `contracts` | суммы ₸, даты, № договора, предмет/направление, `kato_code` | Бюджетные факты о юрлицах |
| `participants` | связь объявление↔организация, `is_winner` (флаг победителя; счётчик участников — производный) | Юрлица |
| `acts` | `act_date`, **`signer_info` (ФИО + должность подписанта)** | **Служебная информация должностного лица** (§6.2.4) — не частная жизнь |
| `rnu_entries` | запись реестра недобросовестных поставщиков | Юрлица (цитата официального реестра) |
| гео-объекты | координаты объекта закупки | Не ПД |

**Два чувствительных края — разобраны явно:**

1. **`acts.signer_info` (ФИО/должность подписанта акта)** — публикуется как **служебная информация
   должностного лица** в связи с исполнением обязанностей, **не** как частные данные (§6.2.4, PRD §7.2).
2. **«ОколоПД»-элементы — хранятся, но НЕ публикуются** (видны только системе), юр-оценка хранения — в §3 (OQ-2):
   - **`subscriptions.telegram_chat_id`** — идентификатор Telegram-чата подписки (доставка уведомлений).
   - **`error_reports.contact`** — опциональный контакт гражданина в канале «Сообщить об ошибке» (FR-28, Story 5.4;
     поле необязательное, без аккаунта, §7.2). [Source: migrations/0011_error_reports.sql]
   Это **единственные два** «околоПД» элемента MVP; ни один не выводится в публичный слой.

[Source: конкурсный §6.2.4 (должностные лица — служебная инфа), §6.3 (MVP только открытые данные); PRD §7.2 (приватность), §10/§11.2 (нет ПД-контура на MVP), глоссарий (БИН не ПД); data_model §B/§C/§F (`organizations`/`acts.signer_info`/`subscriptions.telegram_chat_id`)]

## 3. OQ-2: хранение персональных контактов → очередь юристу (AC3)

**Канонический OQ-2 — `telegram_chat_id`:**

- **Что храним:** `subscriptions.telegram_chat_id` — идентификатор Telegram-чата, связывающий Подписку с Районом (UC-06).
- **Зачем:** доставлять уведомления «мой район» подписчику (FR-24…FR-26). Без chat_id адресная доставка невозможна.
- **Где:** в проекционной БД (👤 **предполагается хостинг в РК** — задел §6.2/§7.2, **подтвердить**; сама
  data-residency — часть этого же вопроса юристу, не решённый факт).

**Родственный вопрос — `error_reports.contact`** (тот же класс «околоПД», §7.2):

- **Что храним:** `error_reports.contact` — опциональный контакт гражданина в канале «Сообщить об ошибке» (FR-28,
  Story 5.4). Поле **необязательное**, без аккаунта; заполняется по желанию отправителя.
- **Зачем:** обратная связь по сообщению об ошибке данных.
- Та же открытая часть — политика хранения/удаления. [Source: migrations/0011_error_reports.sql]

**Открытая часть (вопрос юристу — по обоим элементам):** нужна ли на MVP **политика обработки/удаления** хранимых
контактов (`telegram_chat_id`, `error_reports.contact`) — срок хранения, удаление при отписке/по запросу,
информирование пользователя?

- **👤 Вопрос поставлен в очередь юристу** (OQ-2 + родственный по `error_reports.contact`). Владелец вопроса —
  ответственный за юр-контур (§1.2).
- **Гейт:** ответ по `telegram_chat_id` — **ДО публичного запуска бота** (Story 7.2 — подписки/fan-out — и запуск
  бота ждут токен/3.7-bootstrap, этот же момент гейтит OQ-2); ответ по `error_reports.contact` — **до публичной
  доступности** канала «Сообщить об ошибке».
- **Статус:** 🟡 **в очереди, не закрыт.** До ответа — не открывать соответствующую поверхность публично.

[Source: PRD §7.2 (`telegram_chat_id` — «подтвердить с юристом до публичного запуска бота»), §13 (риск «telegram_chat_id без юр-оценки»), §14 (OQ-2); architecture.md:97 (telegram_chat_id — околоПД, OQ-2); data_model §F (`subscriptions.telegram_chat_id`); migrations/0011_error_reports.sql (`error_reports.contact`); epics.md Epic 7 (7.2 — подписки/уведомления)]
