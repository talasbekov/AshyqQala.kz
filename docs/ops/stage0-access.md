# Stage-0: доступ к ows_v2 (Story 0.1)

> **Назначение.** Зафиксировать официальный канал доступа к данным goszakup (`ows_v2` по
> токену) для Гейта №0 и будущего импорта: схему хранения/ротации токена, статус доступа к
> эндпоинтам (200 OK), КАТО-карту районов Астаны и определение фильтра направлений.
>
> **Принцип проекта:** *официальный канал, не парсинг* (несущий инвариант, §6.1/§6.4) и
> *честность над домыслом* — неподтверждённое помечается «нет данных», а не выдумывается.
>
> **Статус истории:** in-progress. Часть AC — человеко-операционные действия (👤), требующие
> живого `GOSZAKUP_TOKEN`. Токен на момент заполнения **не получен** (ожидается через профиль
> участника goszakup.gov.kz). Все пункты, зависящие от живого токена, ниже помечены
> 🔴 **НЕТ ДАННЫХ — требует живого токена**. Заполнить после получения токена.

## 1. Хранение и изоляция токена (AC1) 👤

**Действие получения токена — человеко-операционное; dev-агент документирует только схему,
без значения токена.**

### Схема хранения

| Параметр | Решение |
|---|---|
| Где хранится | Секрет-стор VPS / переменная окружения `GOSZAKUP_TOKEN` (или `.env` вне репозитория) |
| В репозитории | **Никогда.** Значение токена не коммитится и не приводится в этом документе |
| Защита в git | ✅ `.gitignore` уже содержит `.env` (проверено: блок «env file»). Токен в `.env` в git не попадёт |
| Владелец | 🔴 **НЕТ ДАННЫХ** — назначить ответственного (вопрос владельцу) |
| Ротация | По регламенту владельца токена; при ротации обновляется только секрет-стор/`.env`, код не меняется |

### Изоляция доступа (несущий инвариант на будущее)

В целевой архитектуре токен видит **только** будущий `cmd/importer` (читает источник и пишет в
БД). `cmd/api` (публичное чтение) токена **не видит** никогда. Секрет — в env/секрет-сторе VPS,
вне репозитория, с ротацией.
[Source: `_bmad-output/planning-artifacts/architecture.md` строки 100, 390–391]

### Базовый доступ

- **Базовый URL:** `https://ows.goszakup.gov.kz/v2` [Source: `stage0-audit/main.go:14`]
- **Авторизация:** Bearer-токен. 🔴 **НЕТ ДАННЫХ** — точный формат заголовка подтвердить на
  живом токене (намеренно не берём из памяти модели).


- Кандидаты имени поля: `count`, `cnt_supplier`, `offers_count`, `participant_count`
  [Source: `stage0-audit/models.go:41`]
- На синтетических фикстурах резолвится `trd-buy → "count"`.
- 🔴 **НЕТ ДАННЫХ** — подтвердить **реальное** имя поля на живом токене (блок «Резолв поля

## 4. Фильтр направлений «дороги» / «водоснабжение» (AC4)

### Что уже определено в инструменте (подтверждено, токен-независимо)

Классификация — по тексту предмета закупки (поле `name_ru` лота, подтверждено probe-схемой).
Списки ключевых слов (рус+каз) уже существуют — **переиспользуются, не пишутся заново**:

- **Дороги** [`config.go:36`]: `дорог, автодорог, асфальт, улиц, тротуар, магистрал, проезж,
  дорожн, жол, көше, автомобиль дорог`
- **Вода** [`config.go:40`]: `водоснаб, водопровод, канализац, водовод, питьев, водозабор,
  сети водоснабжения, сумен жабдық, су құбыр, кәріз`

### Открытое решение

- Текущая классификация — **только по тексту**. Нужен ли дополнительно фильтр по **коду
  закупки** — решается на живой выборке. 🔴 **НЕТ ДАННЫХ**.
- Доля совпадений ключевых слов на реальной выборке (применимость списков): 🔴 **НЕТ ДАННЫХ —
  требует живой выборки лотов/договоров** (`go run . -sample N` с токеном; Step B аудита).

**Вопрос владельцу / следующий шаг:** на живой выборке (≥200–500 лотов) замерить долю
покрытия `RoadKeywords`/`WaterKeywords` по `name_ru` и зафиксировать, нужен ли фильтр по коду
закупки.

⚠️ **Нельзя измерить через `-source scrape`:** парсер портала отбирает лоты поиском *по этим же
словам направлений* (`scrape.go:129`, `filter[name]`), т.к. по голому КАТО портал отдаёт в
основном «прочие». Доля направлений на keyword-отобранной выборке циркулярна и не показательна.
Непредвзятая выборка по КАТО доступна только через живой API (по токену). Проверено разовым
прогоном `-source scrape -sample 30` (2026-06-19): получены реальные лоты Астаны, поля
`amount, name_ru, ref_kato, trd_buy_number_anno`; классификация дала 30/30 «дороги» — это
артефакт keyword-фильтра, не сигнал.

## 6. Промежуточное решение: парсер-первый (2026-06-19)

Владелец решил: **временно основной источник — парсер публичного портала** (`-source scrape`);
официальный токен `ows_v2` будет получен и подключён позже. Это **осознанный временный override
несущего принципа §6.1/§6.4** («официальный канал, не парсинг» — «принципиально для юридической
чистоты»). Конфликт был явно показан владельцу до принятия решения.

**Эмпирически подтверждённый потолок парсера** (разовый прогон 2026-06-19):

| Может (без токена) | НЕ может (нужен токен ows_v2) |
|---|---|
| Лоты Астаны (поля `amount, name_ru, ref_kato, trd_buy_number_anno`) | Договоры — центральный объект данных `contracts` |
| Геообъекты/карта (по `ref_kato` + `name_ru`) | Участники (поле в `trd-buy`) → флаг **FR-19** |
| Грубая агрегация по КАТО | РНУ → флаг **FR-22** |
| | Суммы договоров → ценовые бенчмарки, медианы, монополия (**FR-20/FR-21**) |

⚠️ **Влияние на продукт:** на парсинге можно собрать только тонкий срез «карта лотов +
направления». Карточки контрактов и 3 из 4 флагов риска (FR-19/FR-20/FR-21/FR-22) **не строятся**
без токена. Выборка лотов к тому же keyword-смещена (см. AC4). Это расхождение с архитектурой
уровня стратегии → рекомендуется оформить через `correct-course`, а не правкой внутри story.

**Story 0.1 при этом остаётся заблокированной на токене:** её AC — про подтверждение
*официального* канала (200 OK на авторизованных эндпоинтах), парсинг их не закрывает.
