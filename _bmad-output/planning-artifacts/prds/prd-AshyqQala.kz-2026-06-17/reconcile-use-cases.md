## A. ПРОБЕЛЫ (требования/потоки/краевые случаи отсутствуют или искажены)

### A1. [Высокий] UC-08: автозапуск UC-11 (флагов) после импорта учтён, но автозапуск перерасчёта медиан/бенчмарков — нет
- **UC-08 (исходник):** «дозагрузка договоров/лотов/участников/РНУ/актов → … → запуск UC-09 и UC-11».
- **PRD FR-1 Consequences:** «По завершении импорта автоматически запускается нормализация (FR-2) и пересчёт флагов (FR-19…FR-23)».
- **Пробел:** FR-20 (аномальная цена) и FR-18 (медиана района) зависят от кэша медиан (`price_benchmarks`, addendum §2). В цепочке автозапуска после импорта пересчёт/инвалидация кэша медиан явно не указан. Флаг цены может строиться на устаревшей медиане. Стоит добавить в FR-1 Consequences пересчёт `price_benchmarks` как часть постимпортного конвейера.

### A2. [Средний] UC-04 E1 «расширить фильтры» отражён, но альтернатива A1 «Поиск по БИН/наименованию» в UC-04 и в FR-16 разнесены без явной связки сценария поиска внутри фильтрации
- **UC-04 (исходник):** Основной поток фильтры → список; «A1. Поиск по БИН/наименованию». То есть поиск — часть единого сценария поиска/фильтрации.
- **PRD:** Фильтрация — FR-15, поиск по БИН/наименованию — FR-16 (отдельная фича §5.6 совмещает оба). Связка корректна, существенного пробела нет. **Низкий риск** — отмечено для полноты, не блокер.

### A3. [Высокий] UC-02 A1 «акт `/v2/acts`: дата И ПОДПИСАНТ» — в PRD есть, но потеряна явная привязка «служебная информация должностного лица» как осознанное юр-решение на уровне FR
- **UC-02 (исходник):** «A1 (MVP). Есть акт `/v2/acts` — дата и подписант».
- **PRD FR-11 Consequences:** «При наличии акта (`/v2/acts`) показываются дата и подписант (служебная информация должностного лица)». — **Покрыто.** Юр-обоснование продублировано в §7.2. Пробела нет; пункт закрыт.

### A4. [Средний] UC-06 A1 «Смена района» в FR-25 есть, но триггер уведомления «новый ФЛАГ по объекту района» (а не только новый контракт) в UJ-2 описан, во FR-24 — да, но в SM/счётчике событий бот-дайджеста granularность «контракт vs флаг» не зафиксирована
- **UC-06 / UJ-2:** «уведомление при новом контракте/флаге»; UJ-2: «приходит уведомление о новом флаге по объекту его района».
- **PRD FR-24 Consequences:** «При новом Контракте/Флаге в Районе подписчику уходит уведомление». — **Покрыто.** Пробела нет.

### A5. [Средний] UC-11 «снятие флага автоматическое» — покрыто, но правило «авто-снятие РНУ-МЕТКИ на карточке подрядчика (UC-03)» отдельно от флага
- **UC-03 (исходник, MVP-часть):** «если БИН в `/v2/rnu` — метка со ссылкой на источник».
- **PRD FR-14 Consequences:** «Метка снимается автоматически при выходе БИН из реестра (по `end_date`)». — **Покрыто** (совпадает с FR-22). Пробела нет.

### A6. [Высокий] UC-01 E1 «Карта не загрузилась → текстовый список района» — покрыто FR-9, но UC-01 A1 «Объект без геопривязки — через поиск» в FR-9/FR-7 явно не связано с фолбэком первого экрана
- **UC-01 (исходник):** «A1. Объект без геопривязки — через поиск (UC-04). E1. Карта не загрузилась → текстовый список района».
- **PRD:** FR-7 «негеопривязанные — не на карте»; FR-16 «Негеопривязанные объекты доступны через поиск и помечены „без точки на карте"»; FR-9 фолбэк. — Все три краевых случая покрыты, но распределены по разным FR. **Низкий-средний риск:** связка «карта → поиск для негеопривязанных» как пользовательский путь есть в UJ-1 (краевой случай). Существенного пробела нет.

### A7. [Средний → реальный пробел] UC-09 E1 «Конфликт БИН↔наименование → ИЗОЛЯЦИЯ» отражён в FR-2 (`conflict`), НО UC-09 A1 «Неоднозначные → очередь оператору» и поведение системы при незакрытой очереди (что показывается публично по неразрешённому БИН) не специфицировано
- **UC-09 (исходник):** «A1. Неоднозначные → очередь оператору. E1. Конфликт БИН↔наименование → изоляция».
- **PRD FR-2:** очередь `manual` и изоляция `conflict` есть. — **Покрыто по механике.** Пробел тонкий: не задано, как карточка/агрегаты подрядчика (FR-13) ведут себя, пока БИН в `manual`/`conflict` (показывать ли агрегаты по неканонизированной сущности). FR-13 говорит «по каноническим Организациям (после нормализации)» — значит до нормализации агрегат не строится; это разумно, но явного правила «не агрегировать неразрешённое» в acceptance нет. Стоит уточнить.

### A8. [Высокий] UC-10 E1 «Адрес некорректен → объект без карты, ПОМЕЧАЕТСЯ» — покрыто FR-5, но gap: UC-10 не имеет в PRD явного acceptance, что негеопривязанный объект остаётся в скоупе ИМПОРТА/СТАТИСТИКИ района (не выпадает из агрегатов FR-17)
- **UC-05 (исходник):** агрегаты района (число объектов, суммы, медиана).
- **Пробел:** Если негеопривязанный объект без `district_id` (КАТО не распознан), он может не попасть в агрегаты района (FR-17) и медиану (FR-18). Исходник FR-4 присваивает район по КАТО независимо от точки. Стоит явно зафиксировать: район определяется по КАТО даже без точки на карте, иначе негеопривязанные объекты искажают полноту агрегатов района. Это краевой случай, не покрытый acceptance criteria FR-17.

## B. КАЧЕСТВЕННЫЕ / ФОРМУЛИРОВОЧНЫЕ ПОТЕРИ (тон, «человеческий язык», нейтральность, «нет данных»)

### B1. [Высокий] Правило «недостаточно данных» / «нет данных без домыслов» сохранено, но НЕ единообразно как сквозное ограждение
- **Исходник** последовательно требует: UC-02 E1 «нет данных»; UC-11 «недостаточно данных»; глобальное правило формулировок (стр. 5): «недостаточно данных» — допустимая формулировка.
- **PRD:** есть в FR-10 («нет данных» без домыслов), FR-18/FR-20 («недостаточно сопоставимых данных»), NFR-8. — **Хорошо покрыто.** Минорно: нет единого пункта в §7 (ограждения), который бы поднимал «нет данных / недостаточно данных» до уровня сквозного несущего правила, как §7.1 для «сигнал, требующий проверки». Сейчас оно размазано по FR/NFR. Рекомендация: вынести в §7 как явное ограждение наравне с нейтральностью формулировок.

### B2. [Средний] Тон карточки контракта при отсутствии части полей
- **UC-02 E1 (исходник):** «Данные неполны → „нет данных"».
- **PRD FR-10:** «отсутствующие помечаются „нет данных" без домыслов». — Покрыто. Закрыто.

### B3. [Высокий] UC-03 «профиль неполный» — формулировка нейтральности сохранена, но потерян оттенок: исходник строит карточку «из договоров» при отсутствии БИН в справочнике
- **UC-03 E1 (исходник):** «БИН не найден → карточка из договоров, „профиль неполный"».
- **PRD FR-13:** «Карточка строится даже при неполном профиле (помечается „профиль неполный")». — Покрыто. Закрыто.

### B4. [Средний] Запрет обвинительной лексики на флагах — перенесён точно
- **Исходник (стр. 5, UC-11):** «не „нарушение", не „коррупция", не „виновен"».
- **PRD FR-12 / §7.1:** «без слов „нарушение"/„коррупция"/„виновен"». — Точное совпадение. Закрыто.

## C. ПРАВИЛА (фолбэки, авто-снятие, «без домыслов») — проверка на искажение

### C1. [Высокий] Авто-снятие флагов — корректно (FR-19, FR-22, FR-23: «снятие автоматическое»). Без искажений.

### C2. [Высокий] Фолбэк при недоступности API (UC-08 E1) и смене схемы (UC-08 E2) — точно перенесены в FR-3 (локальная копия + алерт; стоп импорта + алерт + тикет на мониторинг НПА). Без искажений.

### C3. [Высокий] Фолбэк карты (UC-01 E1) + фолбэк низкого автопокрытия (UC-10 Go/No-Go ≥70%) — объединены в FR-6/FR-9. Корректно, даже усилено (явный режим «районы + поиск»).

### C4. [Средний] «Флаг без данных не строится» — UC-11 acceptance перенесено в FR-23 и FR-20 (медиана < min_sample). Корректно.

### C5. [Низкий, пробел-уточнение] UC-09 E1 «изоляция конфликта» переведено в статус `conflict` «требует проверки» — формулировка нейтральна, корректно. Но публичное поведение по изолированной сущности не определено (см. A7).

## D. СВОДКА ПРИОРИТЕТНЫХ ДЕЙСТВИЙ

1. **A1 (Высокий):** В FR-1 Consequences добавить пересчёт/инвалидацию кэша медиан (`price_benchmarks`) в постимпортный конвейер — иначе FR-18/FR-20 на устаревшей медиане.
2. **A8 (Высокий):** Зафиксировать в acceptance FR-4/FR-17, что Район присваивается по КАТО даже без точки на карте; негеопривязанные объекты не выпадают из агрегатов/медианы района.
3. **A7 (Средний):** Уточнить публичное поведение карточки/агрегатов подрядчика, пока БИН в очереди `manual`/`conflict` (не агрегировать неразрешённое — формализовать в acceptance FR-13).
4. **B1 (Высокий, качество):** Поднять правило «нет данных / недостаточно данных без домыслов» в §7 как сквозное несущее ограждение наравне с нейтральностью формулировок (сейчас размазано по FR-10/18/20/NFR-8).

**Вывод:** Сознательно исключённый контент этапов 5/6 не репортится. В MVP-скоупе серьёзных упущений потоков нет; основные пробелы — два конвейерных краевых случая (медианы после импорта; район по КАТО без геоточки) и одно качественное ограждение («нет данных» как сквозное правило).
