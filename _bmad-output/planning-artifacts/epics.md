# AshyqQala.kz - Epic Breakdown

## Overview

Этот документ содержит полную разбивку на эпики и истории для **AshyqQala.kz** (MVP — «читающая
версия»), декомпозируя требования PRD, UX-дизайна (EXPERIENCE.md + DESIGN.md) и архитектуры в
реализуемые истории. Скоуп — только MVP (UC-01…UC-11). Этапы 5–6 (кабинеты, оценки, этапы работ,
приёмка, AI, API) — сознательно вне этого документа.

> **Два несущих гардрейла сохраняются в КАЖДОЙ истории:**
> 1. **Нейтральность.** Любой риск-флаг — «сигнал, требующий проверки», никогда «нарушение /
>    коррупция / виновен». Флаги пересчитываемы третьим лицом (`evidence` + `methodology_version`);
>    формулы намеренно простые (отклонение цены ×1.5, а не MAD).
> 2. **Честность над домыслом.** Отсутствие данных → «нет данных»; недостаточная выборка →
>    «недостаточно сопоставимых данных». Платформа не интерполирует и не выдумывает факты.

## Requirements Inventory

### Functional Requirements

Источник — PRD §5 (FR-1…FR-28). Полные testable-следствия каждого FR — в PRD; здесь — формулировка
требования.

**Импорт и нормализация (UC-08, UC-09):**
- **FR-1:** Система ежедневно дозагружает изменённые записи через `/v2/journal`
  (create/update/пометка `is_deleted`); по завершении автоматически запускает нормализацию (FR-2),
  пересчёт флагов (FR-19…23) и пересчёт кэша медиан `price_benchmarks` (FR-18/20).
- **FR-2:** Нормализация вариативных написаний Организаций к одному каноническому БИН: однозначные —
  автоматически; неоднозначные — в очередь оператору (Directus, `manual`); конфликт «БИН↔наименование» —
  изоляция (`conflict`, «требует проверки»).
- **FR-3:** Устойчивость к недоступности и смене схемы API: при недоступности источника публичная часть
  отдаётся из локальной копии + алерт; при смене схемы импорт останавливается + алерт + тикет на
  мониторинг НПА.

**Геопривязка (UC-10):**
- **FR-4:** Автоматическая геопривязка — кандидат точки/Района по адресу и КАТО (`geocode_status=auto`,
  `confidence`); присвоение Района по КАТО.
- **FR-5:** Полуручная разметка через Directus — оператор подтверждает/корректирует точку или полилинию
  (для дорог), публикует (`geocode_status=manual`, POINT|LINESTRING); некорректный адрес → «без точки на
  карте», но объект остаётся в поиске.
- **FR-6:** Go/No-Go-гейт автопокрытия — измерение доли автогеопривязки; при <70% включается фолбэк-режим
  (карта на уровне Районов + поиск, FR-9).

**Публичная карта (UC-01):**
- **FR-7:** Карта Астаны с маркерами геопривязанных Контрактов, зум, кластеризация при плотности.
- **FR-8:** Превью объекта на карте (предмет, сумма, подрядчик) и переход в Карточку контракта (FR-10).
- **FR-9:** Фолбэк — текстовый список объектов Района при недоступности карты или автопокрытии ниже порога.

**Карточка контракта (UC-02, MVP-часть):**
- **FR-10:** Отображение данных Контракта — сумма, предмет, Заказчик, Подрядчик, сроки, статус;
  отсутствующие поля → «нет данных»; имена/предмет на русском (`name_ru`/`subject_ru`), хранение `*_kk`.
- **FR-11:** Ссылка на первоисточник goszakup в каждой Карточке; при наличии акта (`/v2/acts`) — дата и
  подписант.
- **FR-12:** Активные Флаги риска на Карточке с формулировкой «сигнал, требующий проверки»; каждый Флаг
  ведёт к объяснению методики (FR-23).

**Карточка подрядчика (UC-03, MVP-часть):**
- **FR-13:** Агрегаты Подрядчика — БИН, список Контрактов, суммы, регионы (КАТО), агрегированные Флаги;
  строится при неполном профиле («профиль неполный»); пока БИН в очереди нормализации (`manual`/`conflict`)
  — «профиль уточняется», флаги не строятся.
- **FR-14:** Метка РНУ со ссылкой на источник при наличии БИН в `/v2/rnu`; авто-снятие по `end_date`.

**Поиск и фильтрация (UC-04):**
- **FR-15:** Фильтрация Контрактов по направлению, периоду, сумме, наличию Флага и Подрядчику; пустой
  результат предлагает расширить фильтры.
- **FR-16:** Поиск по БИН и наименованию Организации (с учётом нормализации); негеопривязанные объекты —
  через поиск, помечены «без точки на карте».

**Страница района (UC-05):**
- **FR-17:** Агрегаты Района — число объектов, суммы, число активных Флагов, список объектов; Район по
  КАТО независимо от Геопривязки (негеопривязанные учитываются в агрегатах и Медиане).
- **FR-18:** Медиана ₸/км Района и сравнение с городской; группа сопоставимости (направление × КАТО ×
  скользящее окно 24 мес); при выборке < `median.min_sample` (5) → «недостаточно сопоставимых данных».

**Флаги риска (UC-11):**
- **FR-19:** Флаг «единственный участник» — при числе Участников = 1 и способе закупки не из
  `flag.single_participant.exclude_methods`; авто-снятие при обновлении данных.
- **FR-20:** Флаг «аномальная цена за км» — цена/км > Медиана × `flag.price_per_km.deviation_factor` (1.5)
  по группе сопоставимости; при выборке < `min_sample` — «недостаточно сопоставимых данных»; для дорог
  цена/км из `length_km`, без длины Флаг не строится.
- **FR-21:** Флаг «монополия в регионе» — доля БИН по сумме ₸ в группе (КАТО × направление) ≥
  `flag.monopoly.concentration_share` (0.5); не ставится при числе Контрактов < `min_group_contracts` (5).
- **FR-22:** Флаг «наличие в РНУ» — активная запись (`start_date ≤ today`, `end_date` пуст/будущий);
  авто-снятие по `end_date`.
- **FR-23:** Пересчитываемость и публичная методика — каждый Флаг хранит `evidence` и
  `methodology_version`; пороги опубликованы; формулы намеренно простые (×1.5, не MAD); снятие
  автоматическое при обновлении данных.

**Telegram-бот подписки (UC-06):**
- **FR-24:** Подписка на Район и уведомления о новом Контракте/Флаге (`telegram_chat_id` ↔ Район; ссылка
  на Карточку).
- **FR-25:** Смена Района и отписка; при блокировке бота подписка деактивируется автоматически.
- **FR-26:** Антифлуд и дайджест — группировка частых однотипных событий (порог конфигурируем, дефолт > 5
  событий по Району за 1 час).

**Шаринг (UC-07):**
- **FR-27:** OG-теги Карточки (заголовок, сумма, превью) для корректного превью в соцсетях/мессенджерах.

**Сообщение об ошибке (§7.1, досудебная защита):**
- **FR-28:** Публичный безаккаунтный канал «сообщить об ошибке» в данных Карточки/Флага и запросить
  исправление; обращение фиксируется и попадает оператору (Directus-очередь).

### NonFunctional Requirements

Источник — PRD §6 (NFR-1…NFR-8), с переопределением NFR-6 в EXPERIENCE.md.

- **NFR-1 (Производительность):** карта загружается и интерактивна < 3 c; открытие Карточки и выдача
  поиска < 1 c (p95). Бюджет с двумя числами: эталон + p95 на медленном устройстве/сети (3G, старый
  Android); деградация list-first.
- **NFR-2 (Масштаб):** сотни–низкие тысячи Контрактов (Астана, дороги+вода, 2 года); 1 000+ MAU и 1 500+
  Подписок к 6 мес; один VPS + Docker Compose. Sizing считать из выхода stage0-audit (OQ-1).
- **NFR-3 (Доступность/свежесть):** публичная часть доступна из локальной копии при недоступности
  источника (FR-3); ежедневный инкрементальный импорт; цель аптайма ~99%. **Локальная БД — проекция/кэш,
  перестраиваемая из снапшотов, а не источник правды** (источник правды — goszakup); RPO/RTO от времени
  перестроения проекции.
- **NFR-4 (Наблюдаемость):** структурное логирование (slog) + `/metrics`; `import_runs`; счётчики
  SM-C1/SM-C2 как тестируемые хуки.
- **NFR-5 (Прослеживаемость):** каждая Карточка ведёт на Первоисточник (FR-11); каждый Флаг пересчитываем
  с версией методики (FR-23) — главная инженерная и юридическая гарантия.
- **NFR-6 (Язык/i18n) — ПЕРЕОПРЕДЕЛЁН EXPERIENCE.md:** язык по умолчанию — **казахский**, переключатель на
  русский. Язык — свойство роли строки: UI-хром = наш голос (kk); доменный факт goszakup = цитата
  первоисточника → переводить молча запрещено, помечается `lang` источника. Машинный перевод цитат в MVP
  запрещён. Поля `name_kk`/`name_ru`, `subject_kk`/`subject_ru` с первого дня.
- **NFR-7 (Адаптивность/доступность):** mobile-first веб; WCAG 2.1 AA (на MVP — ручной smoke-тест, не
  формальный аудит); a11y canvas-карты (DOM-маркеры + ARIA-список); список объектов — равноправное
  представление данных (честен к негеокодированному), не проекция карты.
- **NFR-8 (Качество данных):** полнота (сумма/адрес/акт), дедупликация (FR-2), актуальность (FR-1);
  отсутствующие поля — «нет данных» без домыслов.

### Additional Requirements

Технические требования из Архитектуры, влияющие на эпики и истории (особенно Epic 1 / Story 1).

**Стартовый каркас (составной — влияет на Epic 1 Story 1):**
- **AR-1 (Starter / Walking Skeleton S-0):** единого «one-command starter» нет. Frontend —
  `npm create vite@latest web -- --template react-ts` (create-vite 9.x, Node 20.19+/22.12+, React Compiler
  off). Backend — идиоматичный Go-модуль `go mod init ashyqqala/server` (Go 1.26.x). Admin — образ
  `directus:11`. Orchestration — Docker Compose + Caddy. **Первая история — S-0 walking skeleton на
  синтетике (T1→T8):** монорепо-скелет → `compose up db` → миграция таблицы `contracts` → sqlc +
  `GetContractByID` → `cmd/api` chi+pgx (`/healthz`, `/metrics`) → seed-строка → web (Vite+Router+Query,
  экран карточки) → Caddy proxy → один `compose up`. **DoD = байт прошёл Postgres→sqlc→chi→Caddy→React** +
  один Playwright smoke. StrictMode → `useRef`-guard карты с первого коммита.
- **AR-2 (Гейт №0 — вне кода, предусловие демо/импорта):** получить `GOSZAKUP_TOKEN`; запустить
  stage0-audit **Шаг B+** (реальный Nominatim, ≥200) → OQ-1 (объём) / OQ-4 (гео-% как шкала) / OQ-6
  (выборка медиан) + B-1 (снапшот схемы) + ops-baseline; ответить стратегический вопрос «какое демо
  выигрывает при автогео 45%?» → выбрать 3 контракта-истории → `docs/ops/stage0-gate.md`. Гео-% —
  **шкала качества, не обрушитель** (Issues #6).

**Данные и хранение:**
- **AR-3:** PostgreSQL 16 + PostGIS 3.x; pgx v5 + sqlc 1.31.x (`overrides` для `geometry`); goose-миграции
  (единый источник схемы; sqlc читает оттуда); динамический bbox-запрос карты — pgx-raw в
  `internal/store/geo.go`.
- **AR-4:** Граница данных — **ПРОЕКЦИОННЫЕ** таблицы (derived из снапшота, импортёр перестраивает) ⊥
  **КУРАТОРСКИЕ** (ручные гео-правки, normalize-маппинги — импортёр только читает) с разными грантами;
  отдельная граница «публичные данные goszakup ↔ пользовательский контент» (задел ПД этапа 5).
- **AR-5:** Лёгкий снапшот — `snapshot_id` рядом с флагом + дешёвый сырой дамп ответа (JSONB/файл);
  тяжёлый снапшот-стор/event-sourcing отложен до пилота.
- **AR-6:** Read-модели материализуются заранее; `price_benchmarks` — пересчёт «в сторону → атомарный
  swap»; гео-результаты кэшируются в `geo_objects`. Redis не вводим.
- **AR-7 (Поиск):** pg_trgm как основной (substring, language-agnostic; GIN-индексы); FTS только `simple`
  (нет казахской конфигурации; `russian`-стеммер на KZ запрещён); БИН — точный матч; ICU-коллация на
  колонках поиска.

**Импорт-инвариант (Issues #1, критический — обязательная S-0-приёмка):**
- **AR-8:** Идемпотентный импорт — дедуп-ключ `(source, goszakup_<entity>_id)` UPSERT `ON CONFLICT DO
  UPDATE`; `snapshot_id` НЕ в ключе уникальности (as_of-штамп); `snapshot_id` детерминирован; повтор того
  же снапшота = no-op; outbox-вставка в той же транзакции.
- **AR-9:** Атомарный постимпортный конвейер — импорт → пересчёт benchmark (swap) → пересчёт флагов →
  атомарная публикация снапшота; флаг **никогда** не считается против устаревшего benchmark; читатель
  видит снапшот целиком (старый или новый), не полупересчёт.
- **AR-10:** Курируемые столбцы переживают ре-импорт (importer только читает; запись — только Directus).
  **S-0-приёмка: два импорта подряд + одна ручная курация между ними** доказывают: медианы консистентны,
  дублей нет, курируемая правка пережила ре-импорт.

**Граница ows_v2 и контракты-как-код:**
- **AR-11 (decode):** `internal/decode` — единая именованная граница декодирования ows_v2→домен +
  `schema_hash` (detect-and-halt на смене зафиксированного контракта схемы, не тихий 0); golden-снапшот
  ответа ows_v2 + тест декодера. Маппинг `fieldCandidates` из stage0 переиспользуется, политика
  инвертируется: аудит=тихо → прод=стоп+алерт.
- **AR-12 (registry/):** единый источник имён/значений (человек правит только здесь): `methodology_params`
  (версионируемый иммутабельный), `honest_states`, `glossary{kk,ru}`, `taboo_lexicon`, `event_types`,
  `error_codes`. Читается в рантайме. Генераторы: `openapi-typescript` (TS-типы) + `tokens-codegen` (CSS).
  **Перекрёстный тест (~7 осей) + сторожа** — главный анти-дрейф.
- **AR-13 (чистые функции):** `flags/median/normalize/benchmark` — чистые функции без store/IO/реального
  времени (пересчитываемость без БД; домен ⊥ доставки). `internal/clock` (Clock интерфейс + Real/Fixed)
  для детерминизма.
- **AR-14 (нейтральность структурой):** проза флага — только через `render(flag_id, evidence, params,
  locale)` из registry; числовые литералы в шаблонах запрещены (линтер); единый серверный gate «нет пути
  к методике + каналу „Сообщить об ошибке" → флаг НЕ публикуется» для всех каналов (web/OG/Telegram).

**API и коммуникация:**
- **AR-15 (REST/OpenAPI):** chi v5; рукописный OpenAPI YAML (арбитр) → `openapi-typescript` +
  `kin-openapi` response-валидация в Go-тестах; версия — префикс `/api` (без `/v1` на MVP).
- **AR-16 (честные состояния — типизированный двухосевой enum, HTTP 200 не ошибки):** `value_state`
  (`ok`/`no_data`/`insufficient_sample`/`not_comparable`/`stale`/`geocode_pending`/`geocode_failed`/
  `source_conflict`/`redacted`/`not_applicable`/`error`) и `flag_state`
  (`raised`/`not_raised`/`insufficient_data`/`not_published`); закрытый union, рендер обязан иметь
  default-ветку. HTTP 4xx/5xx — только технические сбои.
- **AR-17 (контейнер-состояние, Issues #2):** `container_state` для района/списка —
  `no_contracts`/`no_flags_raised`/`not_geocoded`, видимо отдельной строкой (тишина пустого экрана не
  читается как «всё чисто»).
- **AR-18 (transactional outbox):** O-1 запись бизнес-объекта + outbox-строки в одной транзакции; O-2
  воркер поллит `FOR UPDATE SKIP LOCKED` → `Dispatcher.Send` → `sent_at`; O-3 дедуп по `event_id`; O-4
  retry/visibility-timeout детерминированы через `Clock`. Dispatcher — интерфейс: S-0 `LoggingDispatcher`,
  Telegram-реализация — S-1.
- **AR-19 (wire-форматы):** JSON snake_case (`json`==OpenAPI==`db` тег); деньги — `bigint` тенге, суффикс
  `_tng`, **в JSON строка**; даты `timestamptz` UTC, провод ISO8601 `Z`; геометрия — GeoJSON RFC7946,
  порядок `[lon, lat]`; двуязычный контент — `{value, lang, is_fallback, resolution}`, `lang∈{kk,ru}`,
  `value:null`⇒честное состояние; keyset-пагинация (`limit` def 50/max 200, `cursor`); внешний id —
  natural `goszakup_*_id`, у `geo_object`/`risk_flag` — UUIDv7.
- **AR-20 (OG/пуш во времени, Issues #3):** OG-теги рендерит Go из той же проекции, что и SPA; URL
  OG-картинки версионируется по `methodology_version` (+as_of), `og:image:alt` + версия методики на
  картинке; Telegram-дайджест несёт рамку «сигнал, требующий проверки» в каждом пункте.

**Инфраструктура и наблюдаемость:**
- **AR-21 (hot/cold split):** горячий путь 24/7 — `postgres`, `api`, `web` (статика за Caddy),

- **AR-23 (тайлы):** формат — PMTiles (статический файл через Caddy, без тайл-сервера и per-load платы);

- **AR-24 (изоляция токена/секреты):** `cmd/importer` держит `GOSZAKUP_TOKEN` и пишет; `cmd/api` токена

- **AR-25 (бэкап/ops):** бэкап только Postgres (Nominatim/PMTiles воспроизводимы из `tools/`); один

эпика команда имеет машиночитаемый Go/No-Go-вердикт stage0-audit на живом токене (`-format json`:
`oq1_volume`, `oq4_geo_coverage` с доверительным интервалом и размером выборки, `oq6_sample`,
`verdict: go|no-go`), закоммиченный baseline-артефакт (`stage0-verdict-YYYYMMDD.json`), CI-хук
(`geo_coverage < 0.70 → No-Go блокирует merge в Epic 2/3`), прописанный исход «частичный Go» (ручная
гео-очередь Directus как известная стоимость) с владельцем и датой решения, выбранную стратегию демо
(3 контракта-истории) и зафиксированный ключ идемпотентности импорта. **Standalone:** артефакт-вердикт +
правила пивота; не поставляет пользовательской ценности (enabler), но делает риск видимым и тестируемым.
**FRs covered:** — (несёт AR-2; gate для Epic 2/3)

### Epic 1: Каркас, ядро-контракты и первый читаемый контракт-история (вертикальный срез)
Заложить сквозной «позвонок» платформы и общие контракты — и сразу показать **первую читаемую единицу
ценности целиком**, а не просто скелет. После этого эпика любой видит на карте Астаны **3 захардкоженных
реальных контракта-истории, рассказанных целиком**: карточка контракта → бейдж нейтрального флага (evidence
вписан вручную) → экран методики (формула ×1.5, как пересчитать) → ссылка-первоисточник goszakup ↗ →
минимальная **дверь «Сообщить об ошибке»** (mailto/форма-stub). Это гео-независимый демо-фундамент
(Issues #6), который стоит при любом проценте автогеопривязки; первый WOW — на 2–3 неделе. Хотя бы один
контракт показывает **реальное честное состояние** («без точки на карте»), а не только успех. Команда
располагает монорепо, `registry/` (честные состояния, методика-как-код, запретный лексикон), двухосевым
enum честных состояний, median/flags-сигнатурами (чистые функции на выборку), URL-схемой/постоянным id
карточки, `decode`+schema_hash (на дрейф схемы), `render()`, токенами с codegen, i18n-каркасом (KZ-дефолт),
обёртками `<DataState>`/`<LangValue>`, курация-stub и CI-гейтами. **Standalone:** показуемая
история-вертикаль + полный инструментарий и общие контракты; не зависит от живого API и гейта №0
(синтетика / ручные evidence). **Замещается позже:** ручные evidence → реальным compute (Epic 4);
3 истории → масштабом презентации (Epic 5); скелет-карта → полной картой (Epic 3).
**FRs covered:** FR-10 (+ вертикальный демо-срез поверхностей FR-11/12/23/28 на ручных данных — полные версии в Epic 4/5)

### Epic 2: Живые данные — импорт, нормализация, устойчивость
Наполнить платформу реальными, ежедневно обновляемыми официальными данными goszakup. После этого эпика
гражданин видит настоящие контракты Астаны (дороги+вода), нормализованные к каноническому БИН; данные
дозагружаются инкрементально через `/v2/journal`; при недоступности источника платформа отдаёт локальную
копию + алерт, а при смене схемы безопасно останавливает импорт. Импорт идемпотентен и атомарно публикует
снапшот (флаги/медианы никогда не считаются против устаревших данных); курируемые правки переживают
ре-импорт — отдельная история **«Import idempotency & curation survival»** с property/integration-тестом в
CI. **Entry-criterion:** вердикт Epic 0 = Go (или Go-с-фолбэком). **Standalone:** реальные данные текут в
проекционные таблицы, нормализуются, переживают отказ источника и ре-импорт.
**FRs covered:** FR-1, FR-2, FR-3

### Epic 3: Публичная карта и геопривязка (масштабирование до ≥70%)
Превратить «одну улицу» Epic 1 в полную карту Астаны, на которой Айгуль за ~10 секунд находит свою улицу.
После этого эпика объекты автоматически геопривязываются (адрес/КАТО, batch-Nominatim) и доводятся ручной
разметкой через Directus до целевого покрытия; отображаются маркерами/кластерами/линиями (MapLibre +
PMTiles); тап → превью → карточка; негеопривязанные честно помечены «без точки на карте» и доступны в
списке; при автопокрытии <70% (FR-6) или недоступности тайлов карта честно деградирует в список района без
потери фильтров. **Standalone:** полная карта + превью + фолбэк; строится на скелете карты (Epic 1) и
данных (Epic 2).
**FRs covered:** FR-4, FR-5, FR-6, FR-7, FR-8, FR-9

### Epic 4: Расчётное ядро — 4 флага риска и пересчитываемая методика *(compute, backend-only)*
Построить «логику риска» платформы — её репутационное ядро — как чистый пересчитываемый слой. После этого
эпика система считает четыре нейтральных флага (единственный участник, аномальная цена за км, монополия в
регионе, наличие в РНУ) и наполняет `risk_flags`/`price_benchmarks` с `evidence` + `methodology_version`;
методика — публичные данные (формулы намеренно простые: ×1.5 воспроизводимо вручную); нейтральность
проверяется surface-agnostic property-тестом (lexicon запретов в обеих локалях); недостаточная выборка →
«недостаточно сопоставимых данных», флаг не строится. **Гардрейл приёмки (Sally):** выход Epic 4 НЕ виден
пользователю и НЕ считается «опубликованным флагом» в продуктовом смысле — нейтральная лексика,
evidence-структура и `methodology_version` рождаются здесь как обязательные поля объекта-флага, но
публикуются только в Epic 5 под gate-ом нейтральности. **Standalone:** пересчитываемые флаги и benchmark в
БД; ни одного React-байта — приёмка на данные (SQL/Go-ассерт), не на экран. Строится на median-ядре и
registry (Epic 1) и реальных данных (Epic 2).
**FRs covered:** FR-19, FR-20, FR-21, FR-22, FR-23

### Epic 5: Карточки, методика-экран, шаринг и канал об ошибке *(presentation / trust)*
Превратить посчитанные данные и флаги в полную проверяемую и юридически защищённую публичную картину. После
этого эпика гражданин видит полную карточку контракта (первоисточник, акт) и подрядчика (история, регионы,
метка РНУ) с активными нейтральными флагами; тап по флагу → **методика-экран** (формула, evidence, версия,
дата, ручной пересчёт). Каждый публикуемый флаг сопровождается путём к методике и каналом **«Сообщить об
ошибке»** — **без этого флаг не публикуется (gate нейтральности)**; карточкой можно поделиться нейтральным
серверным **OG-превью** (свойство страницы, развязано с gate). **Standalone:** полная защищённая карточка +
методика + шаринг + канал возражения; read-модели поверх таблиц Epic 4, карточка-скелет/URL из Epic 1.
**FRs covered:** FR-11, FR-12, FR-13, FR-14, FR-27, FR-28

### Epic 6: Поиск, фильтрация и страница района
Дать Данияру-журналисту находить аномалии и сравнивать районы. После этого эпика гражданин фильтрует
контракты (направление/период/сумма/наличие флага/подрядчик), ищет по БИН и наименованию (pg_trgm, с учётом

для FR-18). **Гардрейл:** выход эпика НЕ виден пользователю и НЕ «опубликованный флаг».

> 🚫 **Ожидает токен** (Sprint Change Proposal 2026-06-20). Парсер не даёт участников (FR-19),
> РНУ (FR-22), сумм договоров (FR-20/FR-21) → флаги невозможны на интерим-источнике. На синтетике —
> только каркас/ручные evidence (Epic 1), реальный compute — после живого импорта (Epic 2).

### Story 4.1: methodology_params (иммутабельный) + median/benchmark-движок

As a команда,
I want версионируемый конфиг порогов и пересчитываемый движок медиан,
So that флаги и страница района считаются по одной публичной методике.

**Acceptance Criteria:**

**Given** `methodology_params` как ВЕРСИОНИРУЕМЫЙ ИММУТАБЕЛЬНЫЙ конфиг (правка = новая версия, история не переписывается — требование к DDL)
**When** значение читается
**Then** доступны дефолты: `median.comparability_key = direction×kato×24мес`, `median.min_sample=5`, `flag.price_per_km.deviation_factor=1.5`, `flag.monopoly.concentration_share=0.5`, `flag.monopoly.min_group_contracts=5`

**Given** чистая `median(samples) → (value, state)` (сигнатура из 1.10) + таблица `price_benchmarks`
**When** наполняется кэш медиан
**Then** пересчёт «в сторону → атомарный swap»; при выборке < `min_sample` — состояние `insufficient_sample` (медиана не показывается)

**Given** постимпортный хук (2.4)
**When** импорт завершён
**Then** benchmark пересчитывается ПЕРЕД флагами (флаг никогда не считается против устаревшего benchmark)

**Then** несёт нейтральную формулировку «сигнал, требующий проверки» + «Как это посчитано» + первоисточник + deep-link на форму «Сообщить об ошибке»; голое утверждение о лице запрещено

### Story 7.3: Смена района и отписка (FR-25)

As a Ержан-подписчик,
I want сменить район или отписаться,
So that подписка следует за мной и не навязывается.

**Acceptance Criteria:**

**Given** активная подписка
**When** подписчик меняет район одной командой
**Then** связь подписки переустанавливается

**Given** отписка или блокировка бота
**When** она происходит
**Then** подписка деактивируется (при блокировке — автоматически, по сигналу ошибки из 7.1)

### Story 7.4: Антифлуд и дайджест (FR-26)

As a Ержан-подписчик,
I want сгруппированную сводку вместо потока,
So that всплеск событий не спамит меня.

**Acceptance Criteria:**

**Given** порог группировки (конфиг, дефолт > 5 событий по Району за 1 час)
**When** событий больше порога
**Then** они группируются в дайджест, а не отправляются по одному

**Given** дайджест с флагами (AR-20)
**When** он формируется
**Then** рамка «сигнал, требующий проверки» в КАЖДОМ пункте (не «N сигналов» агрегатом); проходит per-surface рендер-тест (7.1)
